# Установщик «Визуализация данных»

Приложение распространяется как unpackaged WinUI 3, self-contained
`Release x64`. Установщик создаётся Inno Setup 6 и предназначен для всех
пользователей компьютера.

## Источник истины

Поведение прибора описывают его прошивки в корне проекта — `main_LWD_1DDS` и
`main_AUTO_5Tx.txt` для старого поколения, `LWD_1_DDS_ATT_UES.c` для нового.
Это правило действует и здесь: если для проверки собранной
версии нужно понять, что именно приложение отправляет прибору или как
интерпретирует ответ, ответ берётся из прошивок, а не из предположений.

## Источник версии

Единственный источник номера версии:

```text
AMK-Data-Visualization\AMK-Data-Visualization.csproj -> Version
```

`scripts\Build-Installer.ps1` передаёт это значение Inno Setup и создаёт:

```text
installer\Output\DataVisualization-Setup-<version>.exe
installer\Output\data-visualization-version.txt
```

Дублировать номер версии вручную в инструкциях или в файле обновлений не следует.

## Правило номеров версий

Нельзя публиковать другое содержимое под уже использованным номером: клиент
обновления сравнивает версии и может не загрузить такую замену. Если после
сборки установщика в дерево исходников попала хотя бы одна правка, нужен новый
номер и пересборка.

Текущее состояние: собран `DataVisualization-Setup-0.3.1.exe` от 23 сентября
2026 года. Каждый следующий номер берётся потому, что под предыдущим установщик
уже собран, пусть и не опубликован.

**Версия предназначена для проверки на приборе и в каталог обновлений не
публиковалась.** Публиковать её следует только после проверки на целевых
машинах.

`0.3.1` исправляет обмен с **Картографом в режиме LWD 4tx, перепрошитым на кадр
320 байт**. Приложение по типу прибора переводило его на транспорт
фиксированной длины старого Картографа, а прибор новой прошивки отвечает
пакетом с полем длины, как остальные приборы этого поколения: `0x11` — 325
байт. Приложение читало 245 байт, кадр отклонялся, остаток ответа оставался в
порту, и весь дальнейший обмен шёл с ошибкой CRC. Теперь транспорт
фиксированной длины выбирается только для Картографа старой прошивки; ветка
старого Картографа и обмен остальных приборов не менялись.

**Исправление подтверждено на приборе 25 сентября 2026 года** (Картограф
`320349001`): 334 кадра по 325 байт без единого отказа, файл записи побайтово
совпал с принятыми кадрами. Прогон выполнялся сборкой `0.3.1` из дерева
исходников — код тот же, что в установщике, но установка, запуск установленной
копии и автообновление самим установщиком этим прогоном не проверены. Не
выполнялись также запись метрологии и автокалибровка на этом приборе.

Признаки штатной работы в журнале сессии:
`PROBE FRAMED METROLOGY DECODED … frame_size=320 | fixed_length_transport=False`
и `DATA ROUTE | protocol=FRAMED_LEN` на каждом опросе; строки
`PROTOCOL SELECTED | protocol=LEGACY_LOOP_NEXT` быть не должно. Единицы
амплитуд Картографа новой прошивки расходятся с текстом прошивки и ждут ответа
разработчика прибора — см. [`../docs/DEVICE_PROTOCOL.md`](../docs/DEVICE_PROTOCOL.md).

`0.3.0` добавляет две вещи, и обе меняют работу с данными, а не только вид
окон, — отсюда смена средней цифры.

Первое: **отметка времени записи метрологии.** В структуре метрологии появилось
поле по смещению 124 — восемь байт с временем записи в секундах Unix-эпохи.
Приложение проставляет его по часам компьютера в момент записи в прибор или в
файл и показывает в окне метрологии полем «Дата записи» в местном времени.
Поле доступно только приборам новой прошивки: у старой по этим смещениям её
служебная область, и писать туда нельзя. После записи в прибор отметка
дополнительно сверяется перечитыванием — смещение подтверждено пока только
объявлением структуры от разработчика прибора, и расхождение раскладки должно
обнаружиться первой же записью, а не молча испортить служебную область.

**Прошивки с этим полем ещё нет.** Ветка чтения и показа безопасна на любых
данных: нули и неразмеченная память выводятся пустым полем, а не датой 1970
года. Ветку записи в зонд нужно прогнать с открытым журналом обмена сразу, как
появится прошивка: строка `verify OK: signature/serial/timestamp match`
подтвердит, что байты легли туда, куда рассчитывало приложение.

Второе: **акселерометр из служебного заголовка записи `.DEV`.** Одиннадцать
байт перед каждым кадром, которые раньше просто пропускались, теперь читаются.
Быстрый пресет «Акселерометр» выводит четыре кривые — три оси и модуль вектора
— в отсчётах; счётчик записи и температура заголовка попадают в журнал сводкой
при открытии файла. Единицы разработчиком прибора не подтверждены, поэтому ось
подписана «отсчёты», а не `g`. Пресет гаснет для `.bin`, `.biv` и для живых
кадров опроса: заголовка у них нет. Гашение обратимо — при возврате к `.DEV`
кривые восстанавливаются с прежней позицией и видимостью.

Кроме того, `0.3.0` включает проверку двоичной раскладки на старте. Метод
`BinaryLayoutVerifier.ThrowIfInvalid` существовал и раньше, но не вызывался
ниоткуда: смещения полей де-факто не проверялись. Теперь он вызывается в
`App.OnLaunched` до создания главного окна, и при расхождении приложение
отказывается запускаться с записью причины в `amk-winui-error.txt`.

`0.2.9` чинит две вещи, обнаруженные после выхода `0.2.8`.

Первая: **после автообновления не открывались системные диалоги выбора файла и
папки.** Установщик запускал приложение напрямую и передавал ему свой
административный токен, а `Windows.Storage.Pickers` в процессе с повышенными
правами отказывают с `E_FAIL`. Обработчики меню объявлены `async void`, поэтому
исключение уходило мимо кода окна: «Открыть файл данных...» не открывал ничего,
и лечил это только ручной перезапуск. Флаг `runasoriginaluser` тут не работал —
см. раздел «Запуск приложения установщиком». Теперь установщик запускает
приложение через оболочку Windows. Проверять нужно именно после автообновления:
с ярлыка проблема не воспроизводится, а признак успеха — `elevated=False` в
первой строке журнала `amk-winui-lifecycle.txt` в каталоге `%TEMP%`.

Вторая: **загрузка файла в базу могла уронить приложение** — поток загрузки
запрашивал выбор прибора, пока был открыт другой диалог, а WinUI допускает
только один открытый `ContentDialog`. Теперь диалоги показываются по одному.

Заодно все вызовы диалогов выбора собраны в одном месте и сообщают о причине
отказа вместо молчания.

- точные размер и SHA-256 хранятся рядом с setup в автоматически созданном
  `data-visualization-version.txt`; хэш независимо пересчитывается после сборки;
- descriptor указывает на фактическое имя установщика и содержит пересчитанный
  SHA-256;
- в payload лежат `XBF` всех одиннадцати существующих окон — ровно те, что
  перечислены в обязательном списке скрипта сборки.

Что изменилось по версиям: `0.2.0` добавила поддержку приборов с новой прошивкой
(кадр 320 байт); `0.2.1` меняла размер окна метрологии и сделала это неверно —
требуемый размер задан в аппаратно-независимых пикселях, а `ResizeClient`
принимает физические, поэтому на дисплее со 125 % окно выходило на пятую часть
меньше содержимого и обрезало колонки воздушных поправок затухания вместе с
обоими рядами кнопок. `0.2.2` переводит требуемый размер по DPI монитора и
дополнительно убирает сохранение дозаписи в существующий файл между сессиями.
`0.2.3` автоматически нормализует размер интерфейса каждого окна относительно
эталонного масштаба Windows 125 % и пересчитывает его при смене монитора.

`0.2.8` исправляет восстановление кривых при параллельном опросе прибора и
просмотре отдельного файла данных. Если во время опроса 5Tx-прибора открыть
4Tx-файл, T5 временно скрывается, но после возврата к живым данным снова
появляется с прежними цветом, видимостью и позицией без повторного выбора
пресета.

`0.2.7` чинит масштаб окон фиксированного размера. Преобразование масштаба
ставилось прямо на содержимое окна — то есть на элемент, который уже прошёл
разметку и был перепривязан к новому родителю. У развёрнутого главного окна это
работало, а у окон «Связь с БД», «Масштаб окна» и «Метрология» преобразование
выставлялось, но на отрисовку не влияло: содержимое занимало 1/1.25 окна и
оставляло пустое место справа и снизу, а строка пояснения и третья кнопка
уходили за край. Теперь масштаб несёт отдельный слой, создаваемый на месте.
Замерено на машине со 100 %: содержимое окна «Связь с БД» заполняет все 660
точек кадра вместо прежних 515. Заодно приведены к общему масштабу пункты меню
«Файл» — они объявлены в разметке и потому не проходили через построение меню, —
и уменьшено окно масштаба.

Кроме масштаба, `0.2.7` исправляет привязку заметок: путь для них выдавался
только при подключённом приборе, поэтому после отключения заметку по только что
записанным данным поставить было нельзя, хотя кадры оставались на графике, а
файл — на диске. Теперь файл записи сессии помнится до её конца.

`0.2.6` исправляет масштаб выпадающих меню. В `0.2.5` он задавался
преобразованием отрисовки поверх уже открытого popup'а, и это было неверно
дважды: для меню `MenuFlyout`, которое разворачивается в собственном окне,
преобразование не действовало вовсе, а список `ComboBox` разворачивается внутри
окна и масштаб уже наследует — там оно накладывалось поверх и умножало масштаб
на себя. Вдобавок проход запускался по вводу, поэтому размер менялся от
постороннего нажатия. Теперь `ComboBox` не трогается вовсе, а у меню
масштабируется разметка: высота, кегль и отступы пунктов задаются при
построении, и меню пересобираются при смене масштаба. Замерено по пикселям на
машине со 100 %: пункт меню 40 точек против 32 прежних, ровно 32 × 1.25.

`0.2.5` приводило к общему масштабу всплывающие поверхности — выпадающие списки,
меню, панели и диалоги: они живут в отдельном popup-слое окна, куда
преобразование содержимого не достаёт, и на дисплее со 100 % оставались мельче
остального интерфейса. Проверено на диагностической сборке с намеренно
завышенной эталонной константой: на машине со 125 % она даёт тот же эффективный
масштаб 1.25, что у пользователя со 100 %. Кроме того, из окна масштаба убрано
пояснение про компенсацию, значения идут в порядке 85 / 100 / 115 %, а высота
окна увеличена — прежней не хватало, и крайние значения обрезались.

`0.2.4` содержит: амплитудные кривые больше не пропадают из применённой
конфигурации при запуске сессии опроса; файл под активной записью открывается на
чтение; обратный расчёт амплитудного УЭС использует порог «бесконечности» самой
прошивки; масштаб окна приводится к эталонному дисплею с первого кадра и
уменьшается на экранах, где эталонный размер не помещается. В самом установщике
изменены три вещи: приложение после установки и после обновления запускается от
имени пользователя, а не администратора (`runasoriginaluser`); минимальная
система поднята с `10.0` до `10.0.17763`, потому что Windows App SDK требует
Windows 10 1809 и на более ранней сборке установка проходила, а приложение не
запускалось; сообщения об ошибках при тихом обновлении больше не подавляются.

Масштаб окна нельзя проверить на эталонной машине: там компенсация по построению
равна единице. Проверять его нужно на системе с масштабом Windows, отличным от
125 %, и на ноутбуке 1366×768.

`0.2.0` в каталог обновлений не публиковалась. Установщики `0.1.1`…`0.2.1`
остались в `installer\Output` как история; в каталог обновлений публиковались не
все.

Сборка кода текущего дерева выполняется штатным сценарием без ошибок и
предупреждений. Проверка установки и масштаба на целевых устройствах, подпись
и публикация в каталог обновлений остаются за владельцем.


## Сборка

Из корня репозитория:

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./scripts/Build-Installer.ps1
```

Скрипт:

1. очищает изолированные `artifacts\build\win-x64` и `artifacts\publish\win-x64`;
2. выполняет self-contained `dotnet publish` для `Release|x64`;
3. переносит созданные WinUI `DataVisualization.pri` и `*.xbf` из каталога
   сборки в каталог публикации;
4. проверяет исполняемый файл, `runtimeconfig`, `PRI` и перечисленные в скрипте
   обязательные `XBF` окон, библиотеки `Microsoft.UI.Xaml` и загрузчик Windows
   App Runtime;
5. компилирует установщик;
6. вычисляет SHA-256 и записывает файл описания обновления.

При отсутствии любого обязательного файла сборка прерывается до создания
установщика — заведомо неполный setup не создаётся. Параметр `-SkipPublish`
допустим только для повторной компиляции уже проверенного каталога публикации.

## Запуск приложения установщиком

Установщик запускает приложение **через `explorer.exe`, а не напрямую**, и в
обеих строках `[Run]` — и после обычной установки, и после автообновления.

Причина. Установщик работает с правами администратора, и запущенное им напрямую
приложение наследует его токен. Приложение с повышенными правами теряет часть
возможностей Windows: системные диалоги выбора файла и папки
(`Windows.Storage.Pickers`) отказывают с `E_FAIL`, окно не принимает
перетаскивание файлов из Проводника, а при разных учётных записях пользователя и
администратора настройки и журналы уходят в чужой профиль.

Флаг `runasoriginaluser` эту задачу не решает. Документация Inno Setup: флаг «не
имеет эффекта», если Setup запущен через «Запуск от имени администратора» или из
уже привилегированного процесса, — потому что у Setup нет возможности выполнить
код от имени исходного пользователя. Приложение запускает setup именно так:
`ShellExecute` с глаголом `runas`. Поэтому флаг молча ничего не делал, и после
автообновления приложение работало с правами администратора до первого ручного
перезапуска — в этом состоянии «Открыть файл данных...» не открывал ничего.

`explorer.exe` уже работает под обычным пользователем, поэтому запущенное им
приложение получает обычный токен независимо от прав установщика.

Проверять это нужно именно после автообновления: при запуске с ярлыка проблема
не воспроизводится. Приложение пишет права процесса первой строкой журнала
журнала `amk-winui-lifecycle.txt` в каталоге `%TEMP%` — `elevated=False` подтверждает, что запуск
корректен.

## Поведение установки

- требуется подтверждение UAC;
- каталог по умолчанию — `Program Files\Визуализация данных`;
- приложение регистрируется в «Установленных приложениях»;
- пользователь отдельно выбирает общие ярлыки меню «Пуск» и рабочего стола;
- стабильный идентификатор приложения позволяет устанавливать новую версию
  поверх существующей;
- после обычной установки мастер предлагает запустить приложение;
- удаление выполняется стандартным деинсталлятором Inno Setup.

## Публикация обновлений

Каталог обновлений:

```text
http://ivanbohg.beget.tech/FilesForProgramVisualisation/
```

В него публикуются установщик и файл описания `data-visualization-version.txt`:

```text
<версия>
DataVisualization-Setup-<версия>.exe
<SHA-256>
```

Первые две строки обязательны, третья рекомендуется и проверяется до запуска
установщика.

При старте приложение через три секунды выполняет тихую проверку обновлений.
Ручная проверка доступна из главного окна. Если версия новее, пользователь
подтверждает загрузку; файл скачивается во временный каталог, проверяется по
имени, размеру, сигнатуре исполняемого файла и SHA-256, затем запускается с UAC.
Режим `/UPDATE=1` перезапускает приложение после установки.

## Порядок выпуска

1. Задать номер версии в `.csproj`, убедившись, что он выше опубликованного и
   ранее не использовался для другого содержимого.
2. Собрать установщик штатным скриптом.
3. Убедиться, что файл описания указывает на фактическое имя установщика и
   содержит его SHA-256.
4. Убедиться, что список обязательных файлов в скрипте включает `XBF` каждого
   существующего окна.
5. Подписать `DataVisualization.exe` и установщик сертификатом.
6. Проверить установку поверх предыдущей версии, оба ярлыка, запуск, удаление и
   автообновление.
7. Опубликовать установщик и файл описания только после ручной проверки.

## Известные ограничения

Каталог обновлений работает по HTTP. SHA-256 защищает скачанный установщик от
незамеченной подмены только при доверенном файле описания и не заменяет HTTPS.
