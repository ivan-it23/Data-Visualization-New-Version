# Протокол обмена с прибором

Документ описывает все команды взаимодействия с прибором, реализованные в
приложении «Визуализация данных», в объёме, достаточном для написания
независимой реализации.

Дата актуализации: **27 августа 2026 года**.

Приборы существуют в двух поколениях прошивки, и приложение работает с обоими:

| Поколение | Кадр измерений | Метрология | Признак |
| --- | --- | --- | --- |
| старое | 240 байт | 240 байт | `сигнатура / 1 000 000 == 0` |
| новое | **320 байт** | 240 байт | старшие разряды сигнатуры содержат размер кадра |

Ветка старой прошивки описана здесь полностью и не менялась. Всё, что относится
к новой, помечено отдельно.

## Источник истины

**Протокол задаёт прошивка прибора.** В корне проекта лежат три файла:

```text
main_LWD_1DDS          — прошивка приборов LWD, старое поколение
main_AUTO_5Tx.txt      — прошивка автономных приборов, старое поколение
LWD_1_DDS_ATT_UES.c    — прошивка нового поколения, кадр 320 байт
```

Состав команд, длины пакетов, содержимое квитанций и действия прибора по каждой
команде проверяются по обработчикам в этих файлах. Ничего не следует
достраивать по аналогии: неверно понятый контракт не вызывает отказа, он даёт
внешне правдоподобные и при этом неверные данные.

Если ответа в прошивке нет, вопрос фиксируется как открытый.

**Прошивка нового поколения получена** — `LWD_1_DDS_ATT_UES.c`. Она и есть
источник истины по новой ветке: `WorkCyclogramStateCommandHandler` (обработчики
всех команд и формат квитанций), `simmetry`, `RO_ARG`, `RO_ATT`,
`get_condition`, `get_sonde_id`, `calc_AM_PH_DFT`, `calc_silent_Tx`, а также
объявление `struct METROLOGY_GP` с раскладкой метрологии нового поколения.
Отладочный проект `TEST_KARTOGRAF_2.0-main` и эмулятор
`new_5Tx_tools_320_bytes_emul` источниками истины больше не являются.

Прошивка поставлена без двух своих заголовков:

- `ExpData.h` — объявления `struct GP_DATA` и `struct ID`. Раскладка кадра
  подтверждена сверкой всех четырнадцати полей с байтами реального ответа
  прибора, но объявлением структуры пока не подтверждена;
- `ModesAndCommands.h` — числовые значения `GetDataCommand`, `SetMetroCommand`,
  `SetAirCommand`, `GetMetroCommand`, `GetSignature`. Соответствие кодам
  `0x11`, `0x12`, `0x1A`, `0x13`, `0x16` подтверждено фактическим обменом с
  прибором, но не текстом заголовка.

Прошивка написана под TMS320 C2000, где адресуемая единица — 16 бит, поэтому
`sizeof` в ней считает слова, а не байты: `sizeof(struct GP_METROLOGY)` = 120,
`sizeof(struct GP_DATA)` = 160. На проводе это те же 240 и 320 байт.

Реализация в приложении:

- `Serial/SerialDeviceService.cs` — команды, выбор транспорта, опрос, запись;
- `Serial/LegacyToolSerialTransport.cs` — транспорт фиксированной длины;
- `Serial/SerialContracts.cs` — коды результатов;
- `Core/Binary/BinaryStructs.cs` — раскладка структур.

> **Оговорка о статусе.** Ветки, помеченные как **подтверждённые**, проверены на
> физическом приборе. Помеченные как **непроверенные** реализованы по прошивке и
> по контракту транспорта, но на приборе не прогонялись. Численное сравнение
> расчётных величин с эталонными данными не выполнялось ни для одной ветки.

## 1. Физический уровень

| Параметр | Значение |
| --- | --- |
| Интерфейс | RS-232 / USB-COM |
| Скорость | **125000** бод |
| Формат кадра | 8 бит данных, без чётности, 1 стоп-бит (8N1) |
| Аппаратное управление потоком | отсутствует |
| Порядок байтов | little-endian во всех полях |
| Таймаут чтения (обычный) | 2000 мс |
| Таймаут чтения (управляющие команды) | 5000 мс |
| Таймаут записи | 2000 мс |
| Размер приёмного/передающего буфера | 4096 байт |

Состояние линий DTR/RTS зависит от выбранного транспорта — см. раздел 3.

После открытия порта нужно очистить приёмный и передающий буферы и выдержать
**150 мс** до первого обмена. Тот же интервал выдерживается после каждой смены
состояния DTR/RTS.

## 2. Контрольная сумма

В обоих транспортах применяется **CRC-16/MODBUS**:

- начальное значение `0xFFFF`;
- полином `0xA001` (реверсивная форма `0x8005`);
- без финального XOR и без реверса результата;
- в пакет записывается **little-endian** (младший байт первым).

```c
uint16_t crc16(const uint8_t *data, size_t length)
{
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < length; i++) {
        crc ^= data[i];
        for (int bit = 0; bit < 8; bit++)
            crc = (crc & 1) ? (uint16_t)((crc >> 1) ^ 0xA001) : (uint16_t)(crc >> 1);
    }
    return crc;
}
```

Тест-вектор для проверки реализации: строка `123456789` → `0x4B37`.

## 3. Два транспорта

Прибор отвечает по одному из двух транспортов. Выбор определяется типом прибора,
а не настройкой пользователя.

### 3.1. Транспорт A — с полем длины

Применяется ко всем приборам, кроме `Картограф LWD 4tx`.

```text
запрос и ответ:
[CMD:1][TOTAL_LEN:2 LE][PAYLOAD:N][CRC16:2 LE]
```

- `TOTAL_LEN` — длина **всего** пакета, включая код команды, само поле длины,
  payload и CRC, то есть `TOTAL_LEN = N + 5`;
- CRC считается по всем байтам пакета, кроме двух последних;
- минимальный допустимый пакет — 5 байт, максимальный — 4096 байт;
- линии: **DTR = 1, RTS = 1**.

Приём ответа: сначала читаются ровно 3 байта заголовка, из них берётся
`TOTAL_LEN`, затем дочитывается `TOTAL_LEN − 3` байт. Пакет с `TOTAL_LEN < 5`
или `> 4096` отбрасывается.

### 3.2. Транспорт B — фиксированной длины (Картограф LWD 4tx)

Применяется только к прибору `Картограф` с четырьмя передатчиками.

```text
запрос и ответ:
[CMD:1][PAYLOAD:N][CRC16:2 LE]
```

- поля длины нет — длина payload известна заранее из типа команды;
- CRC считается по `CMD + PAYLOAD`;
- линии: **DTR = 0, RTS = 0**;
- payload данных и метрологии — **242 байта**: два служебных байта (на реальном
  приборе `0x05 0x06`), затем 240 байт структуры измерений либо метрологии.

### 3.3. Пакеты обоих транспортов совпадают побайтово

Это не совпадение отдельных команд, а общее правило: **транспорт B — это
транспорт A, у которого поле длины отдано в payload.**

| Запрос | Байты | Разбор в транспорте A | Разбор в транспорте B |
| --- | --- | --- | --- |
| чтение кадра | `11 05 00 22 95` | длина `0x0005` | payload `{05, 00}` |
| чтение метрологии | `13 05 00 83 55` | длина `0x0005` | payload `{05, 00}` |
| калибровка воздуха | `1A 05 00 53 57` | длина `0x0005` | payload `{05, 00}` |
| запись метрологии | `13 F5 00 …240… CRC` | длина `0x00F5` = 245 | payload `{F5, 00, …}` |

Отсюда следует важное для реализации: байты `0x05` и `0xF5` в начале payload
транспорта B **не являются подкомандами**. Это младший байт поля длины: 5 для
пакета без данных и 245 для пакета с 240 байтами данных.

Различаются только ответы, поэтому определение транспорта строится на разборе
ответа, а не запроса.

## 4. Сводная таблица команд

| Код | Назначение | Транспорт A | Транспорт B |
| --- | --- | --- | --- |
| `0x11` | чтение текущего кадра измерений | да | да |
| `0x12` | **запись метрологии, только новая прошивка** | да | нет |
| `0x13` | чтение метрологии; запись метрологии в старой прошивке | да | да |
| `0x16` | чтение сигнатуры прибора | да | нет |
| `0x17` | передача выбранного ключа | да | **нет** |
| `0x1A` | калибровка по воздуху | да | да |

Других кодов приложение не отправляет.

Коды команд в новой прошивке строятся как `младший_полубайт | 0x10`
(`variable.h`: `КEY = 0x01 << 4`). Отсюда, в частности, `0x12` для записи
метрологии: у старой прошивки отдельного кода записи нет, там запись идёт тем же
`0x13`, что и чтение, и отличается только длиной payload. **`0x12` не
отправляется приборам старой прошивки** — обработчика этого кода у них нет, и
отправка вслепую нарушила бы то же правило, по которому не отправляется `0x17`
Картографу в режиме LWD 4tx.

Команда `0x17` в транспорте B **не отправляется**: обработчика этого кода нет в
прошивках приборов — там реализованы только чтение кадра, запись метрологии,
калибровка воздуха, чтение метрологии, чтение сигнатуры и вход в загрузчик.
Приложение возвращает ошибку вместо отправки вслепую.

## 5. Команды подробно

### 5.1. `0x11` — чтение кадра измерений

**Транспорт A.** Запрос: `11 05 00 22 95` (payload пустой). Запрос одинаков для
обоих поколений прошивки.

Корректный ответ: `CMD = 0x11`, payload **240 байт** от прибора старой прошивки
либо **320 байт** от прибора новой. Приложение принимает обе длины и сверяет
принятую с той, которую называет сигнатура самого кадра: расхождение означает,
что чтение сдвинулось, и кадр отбрасывается. Ответ с другим кодом команды или
длиной payload, не равной ни 240, ни 320, считается неверным.

**Транспорт B.** Запрос: `CMD = 0x11`, payload `{0x05, 0x00}` → `11 05 00 22 95`.

Ответ: payload **242 байта**. Первые 2 байта служебные, далее 240 байт данных.

Особенности транспорта B:

- **нулевой CRC в ответе допускается** только для этой команды. Прибор в части
  кадров отдаёт `CRC = 0x0000`; это компенсируется обязательной проверкой
  сигнатуры;
- перед приёмом выдерживается пауза **50 мс** после отправки;
- до 2 попыток; повтор выполняется только по таймауту;
- принятый кадр проверяется трижды: разбор сигнатуры, совпадение с ожидаемой
  сигнатурой прибора и признак `Картограф` с четырьмя передатчиками.
  Несовпадение сигнатуры трактуется как ошибка CRC.

### 5.2. `0x13` — чтение метрологии

**Транспорт A.** Запрос: `13 05 00 83 55`.
Ответ: `CMD = 0x13`, payload ровно **240 байт**.

**Транспорт B.** Запрос: `CMD = 0x13`, payload `{0x05, 0x00}` → `13 05 00 83 55`.
Ответ: payload **242 байта**, из них байты 2…241 — метрология.

Особенности транспорта B:

- **нулевой CRC не допускается**, в отличие от чтения кадра;
- до 3 попыток, между попытками пауза **100 мс** и очистка приёмного буфера;
- при первичном определении прибора перед приёмом выдерживается **100 мс**.

### 5.3. Запись метрологии: `0x13` у старой прошивки, `0x12` у новой

Перед записью опрос ставится на паузу и выдерживается **2000 мс**.

Код команды выбирается по поколению прибора, а не подбором:

| Поколение | Команда | Квитанция |
| --- | --- | --- |
| старая | `0x13` с 240-байтовым payload | `CMD = 0x13`, payload 0, 1 или 240 байт |
| новая | **`0x12`** с 240-байтовым payload | `CMD = 0x12`, payload 0 байт |

Старая прошивка возвращает `0x13`, то есть эхо своей команды записи. Новая
320-байтовая прошивка возвращает эхо отдельной команды записи `0x12` без
полезной нагрузки. Фактически зафиксированный пятибайтовый ответ новой прошивки:
`12 05 00 D2 95`. CRC корректна. Для совместимости приложение в новой ветке
также принимает прежний вариант квитанции `0x13`, но произвольные команды не
считает подтверждением записи. Метрология в обоих поколениях занимает ровно
240 байт.

**Транспорт A, старая прошивка.** Запрос: `CMD = 0x13`, payload = **240 байт**
метрологии. Итоговый пакет — 245 байт.

Допустимые ответы: payload длиной **0**, **1** или **240** байт. Payload
240 байт трактуется как считанное обратно состояние и кладётся в кэш. Любая
другая длина — неверный ответ.

**Транспорт B.** Запрос: `CMD = 0x13`, payload **242 байта**:

```text
[0xF5][0x00][METROLOGY:240]
```

Перед приёмом выдерживается **150 мс**. Ответ: payload **2 байта**, нулевой CRC
не допускается.

**Поведение прибора.** Прошивка проверяет присланные воздушные поправки: если
все `Air_zz` нулевые, прибор подставляет собственные автоматически вычисленные
нули воздуха и записывает результат; иначе записывает присланные значения как
есть. Это способ задать нули воздуха вручную.

**Верификация после записи (обе ветки).** Пауза **300 мс**, повторное чтение
метрологии и сравнение сигнатуры и номера корпуса с записанными. Несовпадение
— ошибка. Неудача повторного чтения ошибкой не считается.

### 5.4. `0x16` — чтение сигнатуры

Только транспорт A. Запрос: `16 05 00 93 54`.

Ответ: `CMD = 0x16`, payload **не менее 4 байт**; первые 4 байта — сигнатура
`uint32` (little-endian). Хвост payload игнорируется.

Команда используется при определении прибора. Её неуспех не прерывает
подключение: далее пробуется чтение метрологии.

### 5.5. `0x17` — передача выбранного ключа

Только транспорт A. **Ветка непроверенная.**

Запрос: `CMD = 0x17`, payload **4 байта** — ключ `uint32` (little-endian).
Пример для ключа 1: `17 09 00 01 00 00 00 7D 64`.

Особенность: **таймаут ответа трактуется как успех** — прибор на эту команду
может не отвечать. Если ответ пришёл, но код команды в нём не `0x17`, это
ошибка.

### 5.6. `0x1A` — калибровка по воздуху

Оба транспорта. **Ветка непроверенная на приборе.**

Перед отправкой опрос ставится на паузу и выдерживается **2000 мс**.

**Транспорт A.** Запрос: `1A 05 00 53 57` (payload пустой).
Ответ должен иметь `CMD = 0x1A`; payload не разбирается.

**Транспорт B.** Запрос: `CMD = 0x1A`, payload `{0x05, 0x00}` — на проводе те же
`1A 05 00 53 57`. Ответ: payload **2 байта**, нулевой CRC не допускается. Перед
приёмом выдерживается **150 мс**, чтение идёт с управляющим таймаутом 5000 мс.

**Поведение прибора.** Обработчик одинаков для всех типов приборов:
пересчитывает воздушные поправки `Air_zz` из собственного скользящего среднего
разности фаз, записывает метрологию в энергонезависимую память и только после
этого отвечает квитанцией без данных `[CMD][05][00][CRC:2]` — теми же пятью
байтами, что и квитанция записи метрологии в транспорте A.

Два следствия для реализации:

1. Квитанция транспорта A читается транспортом B без исключений из общего
   правила: там CRC считается по `[CMD][LEN_L][LEN_H]`, здесь — по `CMD` плюс
   два байта payload, а это одни и те же три байта.
2. Ответ приходит только после записи во внутреннюю память, поэтому таймаут
   чтения нельзя опускать до обычных 2000 мс.

Прошивка усредняет фиксированное число измерений, поэтому калибровка, запущенная
сразу после подключения, опирается на неполное окно усреднения.

После успешной калибровки метрологию следует перечитать: новые нули воздуха
находятся в приборе, а не в копии, которую держит приложение.

## 6. Структуры данных

Обе структуры — ровно **240 байт**, упаковка 1 байт, little-endian.

### 6.1. Кадр измерений

Старая прошивка отдаёт 240 байт, новая — 320. **Общая часть не сдвинулась ни на
байт**: первые 240 байт нового кадра побайтово совпадают со старым, а два новых
массива дописаны в конец. Поэтому кадр старого прибора кладётся в первые 240
байт структуры новой, и хвост остаётся нулевым — так же, как это делает
отладочный проект (`read_blok`: `GP_DATA gp_data = {0,}` и чтение
`struct_size` байт).

Индексация каналов: `канал = индекс_частоты * 5 + индекс_передатчика`, где
индекс частоты 0 = 400 кГц, 1 = 2000 кГц; индекс передатчика 0…4 = T1…T5. То
есть в каждом массиве из 10 значений сначала идут T1…T5 на 400 кГц, затем T1…T5
на 2000 кГц.

| Смещение | Тип | Размер | Поле |
| --- | --- | --- | --- |
| 0 | `uint32` | 4 | сигнатура |
| 4 | `uint32` | 4 | байт состояния |
| 8 | `uint32` | 4 | номер кадра |
| 12 | `float` | 4 | температура, °C |
| 16 | `float[10]` | 40 | УЭС |
| 56 | `float[10]` | 40 | симметризованная фаза |
| 96 | `float[10]` | 40 | амплитуда приёмника 1 |
| 136 | `float[2]` | 8 | амплитуда приёмника 1, молчащий канал |
| 144 | `float[10]` | 40 | амплитуда приёмника 2 |
| 184 | `float[2]` | 8 | амплитуда приёмника 2, молчащий канал |
| 192 | `float[10]` | 40 | разность фаз |
| 232 | `float[2]` | 8 | разность фаз, молчащий канал |
| **240** | `float[10]` | 40 | **амплитудные УЭС, только новая прошивка** |
| **280** | `float[10]` | 40 | **симметризованные затухания, дБ, только новая прошивка** |

Массивы из 2 элементов индексируются только частотой (0 = 400 кГц,
1 = 2000 кГц).

### 6.2. Метрология

| Смещение | Тип | Размер | Поле |
| --- | --- | --- | --- |
| 0 | `uint32` | 4 | сигнатура |
| 4 | `uint32` | 4 | номер корпуса (поле «Корпус №» окна метрологии) |
| 8 | `uint16[5]` | 10 | `L1` по передатчикам |
| 18 | `uint16[5]` | 10 | `L2` по передатчикам |
| 28 | `uint16[2]` | 4 | частоты F1, F2 |
| 32 | `int16[10]` | 20 | воздушная поправка фазы |
| 52 | `int16[10]` | 20 | порог амплитуды |
| 72 | `uint32` | 4 | диаметр зонда, мм |
| 76 | `uint32` | 4 | тип работы |
| 80 | `uint32` | 4 | положение приёмника R1 |

Здесь кончается часть, общая для обоих поколений. Дальше раскладка расходится
при неизменном общем размере **240 байт**:

| Смещение | Старая прошивка | Новая прошивка |
| --- | --- | --- |
| 84 | `uint16[78]` — служебная область, 156 байт | `float[10]` — воздушная поправка затухания, дБ, 40 байт |
| 124 | — | `uint16[58]` — служебная область, 116 байт |

Новая прошивка отдала под воздушные поправки затухания первые 40 байт служебной
области. Для прибора старой прошивки эти байты остаются нерасшифрованной
служебной областью: приложение их не показывает и не пишет туда, потому что не
знает их смысла.

Воздушные поправки индексируются так же, как каналы кадра измерений.

## 7. Определение прибора по сигнатуре

Сигнатура `uint32` кодирует тип прибора, число передатчиков, модификацию и — у
новой прошивки — размер кадра измерений.

**Новая прошивка** (отладочный проект, `get_signature` / `get_sonde_id`):

```c
signature = размер_кадра * 1000000
          + тип         *  100000
          + число_Tx    *   10000
          + модификация *    1000
          + номер;
```

Разбор — десятичной арифметикой по всему `uint32`:

```c
uint32_t frameSize = signature / 1000000;      /* 240 или 320 */
uint32_t payload   = signature % 1000000;
uint32_t toolCode  = payload / 1000;
int number         = payload % 1000;
```

Пример: `320151501` → кадр 320 байт, Автоном, 5 Tx, модификация 1, номер 501.

**Старая прошивка** — старшие разряды нулевые (`signature / 1000000 == 0`), и
размер кадра равен 240. Разбор идёт по младшим 20 битам:

```c
uint32_t low20    = signature & 0x000FFFFF;  /* младшие 20 бит */
uint32_t toolCode = low20 / 1000;
int number        = low20 % 1000;          /* номер прибора */
```

В обоих случаях дальше одинаково:

```c
int deviceType    = toolCode / 100;        /* 1 = Автоном, 2 = LWD, 3 = Картограф */
int transmitters  = (toolCode / 10) % 10;  /* допустимо 3…5 */
int modification  = toolCode % 10;
```

**Почему у старой ветки сохранено маскирование.** Сигнатуры приборов в
эксплуатации несут мусор в старших битах: реальное значение `0x3143ADD1`
(826 518 993) полезно только младшими 20 битами, а десятичный разбор дал бы там
«размер 826, тип 518». Отладочный проект маскирования не делает и на таких
сигнатурах ошибается; приложение обязано работать с обоими поколениями, поэтому
использует гибрид: сначала пробуется новая схема и принимается только если в
старших разрядах стоит известный размер кадра (240 или 320) и код прибора
поддерживается, иначе работает старая ветка с маской.

Перебором проверено: ни одна из 12 000 правдоподобных сигнатур новой прошивки
(размеры 240 и 320 × коды 151/152/231/241/242/349 × номера 0…999) не
разбирается старой веткой как поддерживаемый прибор, и наоборот. Обратные
пересечения в пространстве `uint32` существуют, поэтому **размер кадра из
сигнатуры обязан подтверждаться фактической длиной записи**: длиной payload при
опросе и шагом записи при чтении файла.

`number` — серийный номер прибора, поле «Серийный №» окна метрологии. Именно он
совпадает с полем `serial_number` карточки прибора в базе учёта.

Не путать с полем по смещению 4 структуры метрологии: там хранится номер
корпуса, в окне он выведен как «Корпус №».

Поддерживаемыми считаются:

- Автоном с 3, 4 или 5 передатчиками;
- LWD с 3, 4 или 5 передатчиками;
- Картограф **только** с 4 передатчиками (режим `Картограф LWD 4tx`).

Модификация в выборе ветки не участвует. Картограф с иным числом передатчиков
этим контрактом не принимается.

Проверочные примеры из реальных файлов:

| Сигнатура | Кадр | Код прибора | Номер | Расшифровка |
| --- | --- | --- | --- | --- |
| `0x00024FCE` | 240 | 151 | 502 | Автоном, 5 Tx, модификация 1 |
| `0x000386BE` | 240 | 231 | 102 | LWD, 3 Tx, модификация 1 |
| `0x3143ADD1` | 240 | 241 | 105 | LWD, 4 Tx, модификация 1 |
| `320151501` | 320 | 151 | 501 | Автоном, 5 Tx, модификация 1, новая прошивка |

### Масштабирование амплитуд `Картограф LWD 4tx`

Для этой ветки амплитуды приёмников и молчащих каналов передаются в формате
**Q12** и должны умножаться на **1/4096**, чтобы совпасть с общим контрактом LWD
в мВ. Фазы, УЭС, температура и исходные 240 байт не масштабируются. Для всех
остальных приборов коэффициент равен 1.

Масштабирование применяется **только на уровне представления**. В файл кадр
записывается в исходном виде, без изменения.

## 8. Алгоритм подключения и выбора транспорта

```text
1. Открыть порт: 125000, 8N1, без управления потоком, DTR=1, RTS=1.
2. Очистить оба буфера, подождать 150 мс.
3. Если транспорт с прошлой сессии уже известен как фиксированный:
   3.1. DTR=0, RTS=0, пауза 150 мс.
   3.2. Прочитать метрологию по транспорту B (пауза перед приёмом 100 мс).
   3.3. Успех и признак Картограф-4Tx -> транспорт B, выход.
   3.4. Иначе вернуть DTR=1, RTS=1 и продолжить с шага 4.
4. Отправить 0x16 в транспорте A. При успехе запомнить сигнатуру
   (неуспех не прерывает подключение).
5. Отправить 0x13 в транспорте A.
   5.1. Ответ 240 байт -> прибор определён.
        Если сигнатура даёт Картограф-4Tx, переключиться на транспорт B
        (DTR=0, RTS=0) и выйти.
        Иначе остаться на транспорте A и выйти.
6. Метрология в транспорте A недоступна: DTR=0, RTS=0, очистить буферы,
   прочитать метрологию по транспорту B.
   6.1. Успех и признак Картограф-4Tx -> транспорт B.
   6.2. Иначе вернуть DTR=1, RTS=1; прибор не определён.
```

## 11. Запись кадров в файл

Не относится к протоколу, но нужна для совместимости файлов между
реализациями. Подробнее — в [`DATA_FORMATS.md`](DATA_FORMATS.md).

Живые кадры пишутся в файл `.bin` подряд, в исходном виде — ровно те байты,
которые пришли от прибора, без масштабирования: **240 байт на кадр от прибора
старой прошивки и 320 от новой**. Хвост, который приложение дописало при
приведении старого кадра к общей структуре, в файл не попадает: это его
собственные нули, а не данные прибора. Имя
нового файла:

```text
AMK_<номер корпуса>_<диаметр, мм>_<yyyyMMdd_HHmmss>.bin
```

Номер корпуса — поле по смещению 4 структуры метрологии; серийный номер прибора
в имя файла не входит, но его всегда можно получить из сигнатуры любого кадра.

При дозаписи в существующий файл его размер обязан быть кратен размеру кадра
подключённого прибора. Файлы двух поколений в одном файле не смешиваются.

## 12. Что учесть при самостоятельной реализации

1. **Проверяйте сигнатуру, а не только CRC.** В транспорте B для кадров
   допускается нулевой CRC, и сигнатура остаётся единственной защитой от мусора.
2. **Не отправляйте `0x17` на `Картограф LWD 4tx`.** Обработчика этого кода нет
   в прошивке.
3. **Байты `0x05` и `0xF5` в payload транспорта B — это младший байт поля длины
   транспорта A**, а не подкоманды. Пакет транспорта B строится как пакет
   транспорта A, у которого поле длины отдано в payload.
4. **`TOTAL_LEN` в транспорте A включает сам себя, код команды и CRC.** Частая
   ошибка — записать туда длину только payload.
5. **Не сокращайте интервал опроса ниже 700 мс.**
6. **Соблюдайте паузы перед приёмом в транспорте B.** Без них ответ читается не
   полностью и обмен выглядит как таймаут.
7. **Смена DTR/RTS требует паузы 150 мс** и очистки буферов, иначе первый обмен
   после переключения транспорта срывается.
8. **Команды, пишущие во внутреннюю память прибора** (запись метрологии,
   калибровка воздуха), отвечают с задержкой — читайте ответ с увеличенным
   таймаутом.
9. Масштабирование Q12 для `Картограф LWD 4tx` применяйте только при отображении
   и расчётах; в файл пишите сырые байты.
10. **Размер кадра берите из сигнатуры и подтверждайте фактической длиной.**
    Сигнатура называет размер, но одной её недостаточно: подтверждением служит
    длина payload при опросе и повтор сигнатуры на шаге записи при чтении файла.
11. **Не отправляйте `0x12` прибору старой прошивки** — обработчика нет.
12. **Не записывайте воздушные поправки затухания в метрологию старого
    прибора**: по этим смещениям у него служебная область.

## 13. Расчёты новой прошивки

Амплитудная ветка устроена как зеркало фазовой (отладочный проект, `simmetry` и
`RO_AMP`):

```c
att_dB[Tx] = 20 * log10(AM_RX_2[freq][Tx] / AM_RX_1[freq][Tx]);
att_dB[Tx] = sign * att_dB[Tx] - air_att_dB[freq][Tx];   /* sign: +,-,+,-,+ */
att_dB_smt = K * att_dB;                                  /* та же матрица, что для фазы */
```

Обратная задача по затуханию — золотое сечение, целевая величина
`10^(att_dB_smt / 20)` против модуля сигнала прямой задачи. Границы у неё свои,
отличные от фазовой ветки:

| Параметр | Фазовая ветка (`RO_ARG`) | Амплитудная ветка (`RO_ATT`) |
| --- | --- | --- |
| диапазон поиска | 0.01…7000 | 0.01…**1000** |
| признак «бесконечности» | 7200 | **1200** |
| точность величины | 5e-7 | **5e-6** |
| порог «бесконечности» | 5e-9 | **5e-8** |

Порогов у каждой ветки два, и они разные. Первый (`epsilon_ARG` / `epsilon_ATT`)
останавливает поиск, когда невязка стала мала, — это найденное УЭС. Второй
(`epsilon_INF`) срабатывает, когда две пробные точки золотого сечения перестали
различаться, и означает, что величина к УЭС больше не чувствительна, — это
«бесконечность». Приравнивать их нельзя: при равных порогах второе условие
выполняется на первом же шаге и ветка возвращает 7200 или 1200 вместо расчёта.

Величина `att_dB` — отношение амплитуд, поэтому общий масштаб амплитуд в неё не
входит и Q12-приведение результат не смещает.

Байт состояния прибора разбирается одинаково в обоих поколениях: биты 8…12 —
400 кГц T1…T5, биты 0…4 — 2000 кГц.

## 14. Ограничения этого документа

- Приведены только те команды, которые отправляет приложение. Вход в загрузчик
  прибора, реализованный в прошивке, приложением не используется и здесь не
  описан.
- Ветка `0x17` и запись метрологии в транспорте A на приборе целиком не
  прогонялись.
- Калибровка воздуха реализована по обработчику в прошивке и по правилу
  совпадения пакетов двух транспортов, но ни в одной из веток не прогонялась на
  физическом приборе. Первый реальный запуск нужно выполнить с открытым журналом
  обмена: он покажет фактические байты квитанции.
- Подтверждены на физическом приборе: приём кадров и запись файла в режиме
  `Картограф LWD 4tx`, чтение метрологии, определение транспорта.
- Численное сравнение расчётных величин с эталонными данными не выполнялось.
- Служебная область метрологии не расшифрована: 156 байт со смещения 84 у
  старой прошивки, 116 байт со смещения 124 у новой.
- Назначение служебных байтов `0x05 0x06` в ответах транспорта B неизвестно;
  приложение их пропускает.

### Что прошивка нового поколения подтвердила

1. **Транспорт A и его framing.** `GetDataCommand` отвечает пакетом
   `[CMD][LEN_L][LEN_H][320 байт][CRC:2]`, где `LEN = id.struct_size + 5 = 325`,
   а CRC считается по `id.struct_size + 3 = 323` байтам. Поле длины включает
   само себя, код команды и CRC — ровно как описано в разделе 3.1.
2. **Размер кадра берётся из сигнатуры самим прибором.** `id.struct_size =
   сигнатура / 1 000 000`, и именно это значение уходит в поле длины ответа.
3. **Единицы амплитуд — милливольты.** `mV = 0.00023842`, то есть
   `4000 / 2^24`; `AM_RX_1`, `AM_RX_2` и молчащие каналы умножаются на него в
   `calc_AM_PH_DFT` и `calc_silent_Tx`. Q12-приведения у приборов Автоном и LWD
   новой прошивки нет, коэффициент приложения 1 верен.
4. **Раскладка метрологии нового поколения** — объявлением `struct
   METROLOGY_GP`: `air_att_dB[2][5]` со смещения 84, служебная область
   `uint16_t service[58]` со смещения 124. Совпадает с разделом 6.2.
5. **Приведение к воздуху у фазы и затухания устроено по-разному:** у фазы знак
   применяется ко всей скобке `Dir * (d_PH − air_ph / 57297)`, у затухания —
   только к самому затуханию, а поправка вычитается после:
   `Dir * att_dB − air_att_dB`. Раздел 13 описывает это верно.
6. **Квитанции записи метрологии и калибровки воздуха** — пять байт
   `[CMD][05][00][CRC:2]` без полезной нагрузки, у обеих команд одинаково.

### Открытые вопросы по новой прошивке

1. Состояние DTR/RTS для приборов новой прошивки. Прошивка линиями не
   распоряжается — это сторона хоста; приложение для транспорта A выставляет обе
   линии в 1, и на приборе № 502 обмен идёт.
2. Сохраняется ли транспорт фиксированной длины для `Картограф LWD 4tx` после
   перепрошивки и станет ли его payload 322 байта. Полученная прошивка — LWD, о
   Картографе она не говорит. Ветка оставлена без изменений на кадре 240 байт.
3. Как старый прибор реагирует на `0x12` и новый — на `0x13` с payload.
   Обработчика `0x13` с полезной нагрузкой в новой прошивке нет: чтение и запись
   метрологии там разведены по разным кодам.
4. Гарантированно ли нулевые байты в служебной области старой метрологии там,
   где новая прошивка читает `air_att_dB`.
5. `formula_simmetry`, 5 передатчиков, `condition == 0b00001111` (не работает
   T5): `K[T3][T1] = +0.05` при том, что все соседние коэффициенты кратны 0.25.
   Похоже на опечатку вместо `+0.00` или `+0.50`. Приложение повторяет прошивку
   как есть; вопрос разработчику прошивки.

### Дефекты, найденные в прошивке нового поколения

Не влияют на разбор данных приложением, но должны быть переданы разработчику
прошивки.

1. **Переполнение при записи метрологии.** `WorkCyclogramStateCommandHandler`,
   ветка `SetMetroCommand`:

   ```c
   for(int i = 0; i < 240; i++) {
       dataPtr16[i] = (rdataB[2*i])|((rdataB[2*i+1]<<8) & 0xFF00);
   }
   ```

   Счётчик должен идти до 120: структура метрологии занимает 120 слов
   (240 байт), а цикл пишет 240 слов, то есть 480 байт. Первые 120 итераций
   заполняют метрологию правильно, остальные 120 затирают память за структурой
   значениями, прочитанными из `rdataB` за пределами и полученных данных, и
   самого массива (`uint16_t rdataB[256]`, а читается до индекса 479).
   Для сравнения, `writeFlashDataMetrology` тот же перевод делает верно:
   `for(i = 0; i < 120; i++)`.
