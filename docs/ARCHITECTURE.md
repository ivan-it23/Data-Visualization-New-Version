# Устройство приложения «Визуализация данных»

Документ описывает разбиение кода на слои, ключевые контракты и правила, которые
нельзя нарушать при доработке.

## Источник истины

Поведение прибора задают его прошивки в корне проекта:

```text
main_LWD_1DDS      — прошивка приборов LWD
main_AUTO_5Tx.txt  — прошивка автономных приборов
```

Перед изменением обмена с прибором, разбора кадров, единиц величин или расчётов
нужно открыть соответствующий обработчик в прошивке и прочитать его. Контракт,
выведенный по аналогии или по памяти, считается непроверенным до тех пор, пока
не найден в прошивке.

Ошибки этого рода не приводят к падению: они дают график, который выглядит
правдоподобно и при этом неверен.

Технологический профиль: WinUI 3, `net10.0-windows10.0.26100.0`, минимальная
поддерживаемая система `10.0.17763.0`, только x64, unpackaged, self-contained
Windows App SDK. Автоматизированных тестовых проектов нет.

### Правило слоёв

Окна отвечают за отображение и последовательность действий. Разбор двоичных
данных, выбор кривых и расчётные формулы живут в библиотеках. Дублировать их в
коде окон нельзя: это единственная причина, по которой расхождения между
режимами обнаруживаются поздно.

## Вертикали данных

### Файл → график

```text
выбор файла → ToolDataFileReader → ToolDataRepository
            → ChartConfiguration → ChartDataCalculator → LineChartControl
```

### Прибор → график и запись

```text
SerialDeviceService → выбранный транспорт и проверка CRC → разобранный кадр
                    → хранилище первого графика → отрисовка
                    → параллельно запись кадра в файл
```

### Метрология → расчёт

```text
MetrologyWindow → прибор или файл метрологии → MetrologySession
                → ChartDataCalculator → MetrologyCalculator
```

## Контракты, которые нельзя менять без отдельного решения

### Двоичная раскладка

- кадр измерений и метрология — ровно по 240 байт каждая;
- размеры структур проверяются на старте `BinaryLayoutVerifier`;
- индексация каналов: `канал = индекс частоты * 5 + индекс передатчика`, где
  индекс частоты 0 соответствует 400 кГц, 1 — 2000 кГц;
- хранилище держит приведённые к единому виду кадры и отдельную запись о
  возможностях для каждого из них.

Полная раскладка полей — в [`DEVICE_PROTOCOL.md`](DEVICE_PROTOCOL.md).

### Определение прибора и его возможностей

Сигнатура кадра кодирует тип прибора, число передатчиков и модификацию.
Распознавание и построение возможностей сосредоточены в
`ToolDataAdapterRegistry` и `UniversalCanonicalAdapter`. Новые типы приборов
добавляются только через этот слой, а не проверками по месту.

Режим `Картограф LWD 4tx` определяется двумя признаками: тип — `Картограф`, число
передатчиков — 4. Модификация в выборе ветки не участвует. Пятый передатчик в
этом режиме недоступен.

### Масштаб амплитуд

Амплитуды приёмников и молчащих каналов режима `Картограф LWD 4tx` передаются в
формате Q12 и приводятся к общим единицам коэффициентом `1/4096`. Приведение
выполняется **только в слое доступа к данным** (`ToolDataAccessView`): в файл
кадр записывается ровно в том виде, в каком пришёл от прибора. Фазы, УЭС и
температура не масштабируются.

### Хранилище кадров

`ToolDataRepository` владеет кадрами, их метаданными, именем и путём источника,
версией данных, добавлением живых кадров и анализом диапазонов.

Первый график всегда работает с основным хранилищем. Второй график в связанном
режиме читает то же хранилище, а в режиме отдельного файла — собственное. Смена
режима второго графика не должна очищать первый график или удалять его
независимый источник.

### Состояние просмотра

`ChartViewportState` хранит для каждого графика диапазон, масштаб и три стека
истории: общий для кнопки отмены и по одному на каждую ось. Все три пополняются
одновременно, и отмена снимает по элементу с каждого, иначе стеки расходятся.

Стеки осей очищаются везде, где сбрасывается диапазон.

При масштабировании одной оси Y вторая закрепляется на том диапазоне, из
которого сейчас рисуется, причём до добавления отступа: отрисовка добавляет свои
5 % сама, и передача уже расширенного диапазона раздувала бы закреплённую ось на
каждом шаге.

### Происхождение конфигурации кривых

Каждая применённая конфигурация помечается тем, какая поверхность её построила:
окно настройки кривых, оверлей на графике или снимок из заметки. Подсветка
элементов схемы выполняется только для конфигурации, построенной этой же
поверхностью.

Причина: комбинированный выбор нельзя однозначно восстановить из списка кривых.
Восстановление выводило элементы, которых пользователь не выбирал, и подсвечивало
их.

### Учёт возможностей источника

Число передатчиков резолвится единственным методом
`ChartWorkspace.GetAvailableTransmitterCountForGraph`. И окно схемы, и оверлей на
графике обязаны обращаться к нему, а не читать метаданные самостоятельно.

`ChartWorkspace.DropUnsupportedCurvesForGraph` удаляет из применённой
конфигурации кривые отсутствующих передатчиков и пересчитывает оси. Вызывается в
начале отрисовки, поэтому конфигурация, построенная для пяти передатчиков и
оставшаяся после перехода на четырёхпередатчиковый источник, теряет лишние
кривые до того, как их прочитают легенда, схема и список видимости.

Число передатчиков входит в ключ кэша редактора компактной схемы: редактор
создаётся до загрузки данных, и без этой проверки он навсегда оставался бы
пятипередатчиковым.

## Загрузка файлов в базу учёта приборов

Обмен идёт по HTTP с сайтом учёта приборов, а не напрямую с его базой данных:
учётные данные базы иначе пришлось бы положить внутрь установщика. Доступ даёт
токен, который пользователь создаёт в своём профиле на сайте.

Разделение ответственности:

- `AMK.DataVisualization.DeviceRegistry` — протокол, разбор ответов, хранение
  токена и построение имени файла. Ничего не знает об окнах;
- `Services/DeviceRegistryConnection` — состояние связи на время работы
  приложения и единственное место, где выясняется, настроена ли она;
- `Services/DeviceRegistryUploadFlow` — весь сценарий загрузки: определение
  прибора, подтверждение пользователем, отправка, разбор ответа. Живёт отдельно
  от окон, потому что одинаково нужен окну метрологии и главному окну;
- `Views/DeviceRegistryWindow` — ввод адреса и токена.

Правила, которые нельзя нарушать:

- **номер корпуса берётся только из ответа сервера.** В приборе его нет, и
  подставленное значение отправит файл в базу под сочетанием, которого нет ни на
  одной карточке: запись существует, но на сайте не видна;
- **тип прибора определяется по `DeviceType` сигнатуры, а не по `ToolDataKind`.**
  Картограф в canonical-слое помечен как LWD-совместимый и по виду данных ушёл бы
  в чужой тип;
- **соответствие типов хранит сервер.** Приложение отправляет код (`Autonom`,
  `Lwd`, `Cartograph`), сервер переводит его в значение своей базы — иначе две
  копии справочника разойдутся;
- **токен не хранится открытым текстом.** На диск он попадает зашифрованным
  DPAPI для текущего пользователя Windows.

## Диагностика обмена

Диагностика разделена на два потока:

- `DeviceProtocolLog` — подробная транспортная трассировка (отправленные и
  принятые байты, CRC, размеры, таймауты, причины отклонения кадров). Пишется
  только в файл;
- `DeviceExchangeLog` — поток для окна «Логи»: сырые отправленные пакеты,
  краткая строка обмена и расшифровка кадров.

Файловая запись выполняется ограниченной фоновой очередью и не блокирует поток
обмена и интерфейс.

## Правила внесения изменений

1. Перед изменением обмена с прибором — открыть обработчик в прошивке.
2. Не менять размеры кадров, смещения полей, индексацию каналов и единицы
   величин без отдельного решения.
3. Не переносить разбор двоичных данных и расчётные формулы в код окон.
4. Разделять улучшения поведения и исправления контракта: их последствия
   проверяются по-разному.
5. Раздельно фиксировать, что подтверждено сборкой, что запуском, а что
   сравнением с прибором. Успешная сборка не является проверкой работы.
6. Новые типы приборов добавлять через слой адаптеров и возможностей.
