# Форматы файлов и пользовательских хранилищ

Документ описывает всё, что приложение читает и пишет на диск. Раскладка полей
кадра измерений и метрологии приведена в
[`DEVICE_PROTOCOL.md`](DEVICE_PROTOCOL.md) и здесь не дублируется.

## Источник истины

Состав и смысл полей кадра задают прошивки приборов в корне проекта:

```text
main_LWD_1DDS          — прошивка приборов LWD, старое поколение
main_AUTO_5Tx.txt      — прошивка автономных приборов, старое поколение
LWD_1_DDS_ATT_UES.c    — прошивка нового поколения, кадр 320 байт
```

Файлы данных — это ровно те байты, которые прибор выдал по своему протоколу,
поэтому единственный способ проверить смысл поля — прочитать прошивку.

---

## 1. Файлы данных

Все три контейнера содержат структуру измерений прибора. Её размер задаёт
поколение прошивки: **240 байт у старой, 320 у новой**. Расширение файла на это
не влияет — оно определяет только наличие служебного заголовка записи.

| Расширение | Размер записи, старая прошивка | Размер записи, новая прошивка | Смещение данных |
| --- | --- | --- | --- |
| `.bin` | 240 байт | 320 байт | 0 |
| `.biv` | 240 байт | 320 байт | 0 |
| `.DEV` | 251 байт | **331 байт** | 11 |

Оба поколения используют все три контейнера. Порядок байтов — little-endian во
всех полях.

### Как определяется размер записи

Размер кадра закодирован в сигнатуре, и она лежит в начале каждой записи (для
`.DEV` — сразу за служебными 11 байтами). Порядок такой:

1. читается сигнатура первой записи и из неё выводится размер кадра;
2. полученный размер **подтверждается по самому файлу**: на предполагаемом шаге
   в начале следующих записей должна лежать та же сигнатура;
3. если не подтвердился — тем же способом проверяются остальные известные
   размеры;
4. ни один не подтвердился — файл отклоняется с явным сообщением, а не читается
   наугад.

Подтверждение обязательно: сигнатуры приборов в эксплуатации несут мусор в
старших битах, а признак новой прошивки лежит как раз в старших разрядах.

Файл из одного-единственного кадра подтверждать нечем; для него принимается
размер, названный сигнатурой, и только если он совпадает с длиной файла.

Записи двух поколений в одном файле не смешиваются: у всех записей файла одна
сигнатура, а значит и один размер.

### Правила чтения

- файл принимается, если в нём есть хотя бы один полный кадр;
- неполный хвост в конце файла пропускается, его длина сообщается пользователю;
- кадр, не прошедший разбор, пропускается и считается отдельно;
- правило одинаково для всех трёх расширений, так как опирается на размер
  физической записи.

Дамп памяти прибора обрывается там, где остановилась запись, поэтому неполная
последняя запись — штатная ситуация, а не признак повреждения.

Файл, в который прямо сейчас идёт запись живых кадров, открывается на чтение
наравне с остальными: чтение ведётся в режиме совместного доступа и записи не
мешает. В график попадают кадры, дописанные к моменту открытия; незавершённый
последний кадр отбрасывается тем же правилом, что и оборванный хвост дампа.

### Запись живых кадров

Кадры пишутся подряд, ровно в том виде, в каком пришли от прибора, без
какого-либо масштабирования: по 240 байт от прибора старой прошивки, по 320 от
новой.

В памяти приложения кадр всегда приведён к 320 байтам, но дописанный при этом
хвост в файл не попадает — это нули приложения, а не данные прибора, и запись их
сделала бы файл несовместимым с исходной прошивкой. То же правило действует при
сохранении диапазона, вырезании и сборке файла конструктором.

Имя нового файла:

```text
AMK_<номер корпуса>_<диаметр зонда, мм>_<yyyyMMdd_HHmmss>.bin
```

Если номер корпуса и диаметр ещё не прочитаны из метрологии, вместо них
подставляется `Unknown`.

При дозаписи в существующий файл его размер обязан быть кратен размеру кадра
подключённого прибора.

## 2. Файл метрологии

Ровно **240 байт** в обоих поколениях прошивки — структура метрологии в том же
виде, в каком она хранится в приборе. Размер не изменился, но новая прошивка
перекроила служебную область: её первые 40 байт заняты воздушными поправками
затухания. Раскладка обеих версий — в [`DEVICE_PROTOCOL.md`](DEVICE_PROTOCOL.md).

Поколение файла определяется его же сигнатурой, поэтому файл метрологии, как и
файл данных, описывает себя сам. При открытии проверяется, что сигнатура
принадлежит поддерживаемому прибору; файл другого размера не принимается.

Расширение обычно `.bin`. Такой файл записывается кнопкой «Сохранить файл» окна
метрологии и читается кнопкой «Открыть файл».

## 3. Заметки на графике

Файл располагается рядом с файлом данных:

```text
<полное имя файла данных>.notes.jsonl
```

Кодировка — UTF-8 без метки порядка байтов. Формат — построчный JSON, файл
только дописывается: изменение и удаление не переписывают предыдущие строки, а
добавляют новые записи. Итоговое состояние заметки определяется применением всех
строк по порядку.

### Запись создания

| Поле | Смысл |
| --- | --- |
| `noteId` | идентификатор заметки |
| `createdUtcMs` | время создания, мс UTC |
| `configKey` | ключ конфигурации кривых для сопоставления |
| `configSnapshot` | снимок конфигурации для восстановления |
| `presetName` | имя пресета на момент создания |
| `xAxisType` | `FRAME_NUMBER` или `TEMPERATURE` |
| `xIndex` | позиция по оси X |
| `yLeft` | координата по левой оси |
| `hasYRight` | признак наличия правой оси |
| `yRight` | координата по правой оси |
| `anchorAxisGroup` | ось, к которой привязана заметка |
| `text` | текст заметки |

### Запись изменения

```json
{"op":"update","noteId":"...","updatedUtcMs":...,"text":"..."}
```

### Запись удаления

```json
{"op":"delete","noteId":"...","deletedUtcMs":...}
```

Заметки создаются только для первого графика и для второго в связанном режиме.
При работе с прибором файл заметок создаётся только при включённой записи, иначе
заметку не к чему привязывать.

## 4. Границы сегментов собранных файлов

Когда файл собран конструктором из нескольких исходных, границы исходных частей
сохраняются отдельно и рисуются на графике пунктиром.

Расположение:

```text
%LOCALAPPDATA%\AMK-Data-Visualization\segments\<имя файла>.<хэш пути>.segments.tsv
```

Хэш полного пути в имени позволяет различать одноимённые файлы из разных
каталогов. Дополнительно поддерживается чтение файла описания, лежащего рядом с
самим файлом данных.

Формат — текст с полями, разделёнными табуляцией. Для каждого сегмента
сохраняются: позиция начала в собранном файле, число записей, позиция начала в
исходном файле, путь к исходному файлу и подпись сегмента. Символы табуляции и
обратной косой черты в значениях экранируются.

Описание сегментов переносится при вырезании диапазона из файла.

## 5. Настройки приложения

Все файлы настроек — JSON в кодировке UTF-8, каталог
`%LOCALAPPDATA%\AMK-Data-Visualization\`.

| Файл | Содержимое |
| --- | --- |
| `connection-settings.json` | последний выбранный COM-порт, каталог записи, признак включения записи |
| `chart-display-settings.json` | опции вывода кривых на графике, отдельно для первого и второго графика |
| `window-scale-settings.json` | выбранный масштаб окон |
| `device-registry-settings.json` | адрес базы учёта приборов и токен доступа |

В `device-registry-settings.json` токен хранится в поле `ProtectedToken`
зашифрованным средствами Windows (DPAPI) для текущего пользователя и записанным
в Base64. Расшифровать его может только та же учётная запись на том же
компьютере: скопированный файл настроек на другой машине бесполезен.

Интервал опроса намеренно не сохраняется: каждая сессия начинается со
значения 2000 мс. Так же не сохраняется выбор дозаписи в существующий файл
и сам этот файл: иначе следующий запуск молча продолжил бы дописывать файл
прошлой сессии, и пользователь узнал бы об этом только по его содержимому.

Каталог записи по умолчанию — `Рабочий стол\AMK_Data`, он создаётся
автоматически. Явно выбранный пользователем путь сохраняется и не
переопределяется автоматически.

## 6. Журнал обмена с прибором

```text
%LOCALAPPDATA%\AMK-Data-Visualization\Logs\
```

Текстовые файлы в UTF-8, по одному на сессию. Новое подключение прибора и
переход к работе с файлами данных начинают отдельную сессию. Хранятся три
последних файла размером до 32 МБ каждый; при создании четвёртой сессии самый
старый файл удаляется.

В памяти приложения остаются последние 300 записей, они показываются в окне
«Логи» единым потоком.
