## 1. Цель и правила

Цель — перенести файловую, приборную, расчётную и пользовательскую логику
Win32/C++ приложения в модульное приложение WinUI 3 / .NET 10.

Обязательные правила:

- legacy-проект остаётся источником истины до ручной parity-проверки;
- binary layout, размеры кадров, смещения, индексы, единицы и формулы не
  изменяются без отдельного решения;
- UI отвечает за orchestration и отображение, а не за разбор binary-данных и
  метрологические вычисления;
- улучшения поведения отделяются от переноса legacy-контракта;
- build-, runtime- и parity-проверки фиксируются раздельно;
- автоматизированных тестовых проектов нет; функциональная проверка выполняется
  владельцем вручную.

## 4. Рабочие вертикали

### Файл → график

`FileOpenPicker` → `ToolDataFileReader` → `ToolDataRepository` →
`ChartConfiguration` → `ChartDataCalculator` → `LineChartControl`.

### Прибор → live-график и запись

`SerialDeviceService` → выбранный transport/CRC → `ParsedToolFrame` → primary
repository → Graph 1 и связанный Graph 2; параллельно выполняется canonical
recording.

### Метрология → FromComputer

`MetrologyWindow` → зонд или 240-байтовый файл → `MetrologySession` →
`ChartDataCalculator` → `MetrologyCalculator`.

## 5. Границы готовности

- **implemented** — кодовая вертикаль существует;
- **build-verified** — решение или установщик успешно собран;
- **runtime-verified** — пользовательский сценарий реально выполнен;
- **parity-verified** — результат сопоставлен с legacy на тех же данных или
  приборе;
- **release-verified** — проверены установка, обновление, удаление и подпись.

Эти статусы нельзя подменять друг другом.

## 6. Основные риски

- Ошибка binary layout или масштаба может дать визуально правдоподобный, но
  неверный график.
- `FromComputer` нельзя заменять чтением `FromSonde`.
- Graph 2 independent и COM live не должны использовать один глобальный
  repository без явного режима.
- Журнал обмена ограничен 300 элементами в памяти и тремя файлами сессий по
  32 МБ; для физического прибора ещё требуется проверить полноту записей при
  длительном непрерывном обмене и перегрузке очереди.
- Setup `0.1.4` не опубликован, не проверен установкой/автообновлением и уже
  отстал от дерева исходников: он не содержит capability-awareness оверлеев.
- Производительность на больших файлах нельзя считать подтверждённой до
  реализации и измерения LOD/cache.

## 7. Рекомендуемый порядок продолжения

Если владелец не назначил другую задачу:

1. выполнить parity `FromSonde` / `FromComputer` на контрольных данных;
2. повторить полный COM-тест `Картограф LWD 4tx`, включая reconnect,
   метрологию и запись;
3. выделить общую geometry-модель и добавить LOD/downsampling;
4. реализовать reporting;
5. назначить новый номер версии и провести полный release-цикл с code signing.

Оперативный следующий шаг фиксируется в `SESSION_TASKS.md`.
